## なぜこれをやるのか

これまでの検証はすべて**過去データの分割**だった。前半・後半に分ける、四半期に切る、プラセボを置く。どれも必要な手順だが、限界がある。**分けたデータは既に存在していて、私はその全体を一度は見ている。** 「後半では見なかったことにする」という自己申告に頼っている。

今日から先のデータは違う。まだ誰も見ていない。ここで同じ傾向が出れば、どんな分割検証よりも強い証拠になる。

## 検証対象の由来（なぜ 1000PEPE なのか）

6銘柄（BTC / SOL / 1000PEPE / TAO / GOLD / WTI）で donchian を検証し、前半・後半の両方でプラスだったのは 1000PEPE と GOLD の2つだった。

1000PEPE は前半 +12.47% / 後半 +16.63% / 全体 +30.63%（544件、t=+1.68）。パラメータ感度は連続した山で、スプレッドを実測の4倍にしても +27.4% を保った。四半期別では、原資産が +223% の局面でも −46% / −36% の局面でもプラスだった。

**それでも不採用としている。** 理由は2つ。

1. **多重比較.** 6銘柄を試せば、前半・後半が五分五分でも1.5個は「両方プラス」になる。2個残ったのは偶然の期待値そのものである。t=1.68 も「6回引いたうちの最良」であり、単独の1.68とは意味が違う。
2. **少数トレード依存.** 544件のうち上位10件を除くと合計は −99,851 に転じる。

この2点は、**新しいデータを足す以外に解消しようがない**。だから前向きに回す。

## なぜ日数ではなくトレード数か

統計的な確からしさを決めるのは**トレード数**であって経過日数ではない。当初の「90日」は「1銘柄で60件たまるまで」を日数に言い換えただけだった。

銘柄を増やせば同じ件数が早くたまる。実測した取引頻度は6銘柄とも1.5日に1件前後で、合計すると1日約4件。**60件が15日で埋まる**（1銘柄なら92日）。

| | 1銘柄 | 6銘柄 |
|---|------|------|
| 40件 | 61日 | 10日 |
| 60件 | 92日 | 15日 |
| 100件 | 153日 | 25日 |

**基準を緩めたのではなく、同じ証拠を早く集める。**

### プールして判定する（銘柄別に良いものを探さない）

銘柄別に見て「良かったもの」を採るのは、これまで何度も踏んだ多重比較の罠である。6銘柄あれば実力が無くてもどれかは良く見える。前回それで 1000PEPE と GOLD が残り、偶然の期待値（1.5個）とぴったり一致した。

**主判定は全銘柄をプールした1つの数字で行う。** 銘柄別の内訳も出すが、それは記述であって判定ではない。「PEPEだけは良かった」と言い出した時点で、また同じ罠に落ちる。

### 起動直後のエントリーについて（既知のバイアス）

起動時に既にブレイク条件を満たしている銘柄は、その場で建てる。継続稼働していたシステムなら**ブレイクの瞬間に建てて既に保有している**はずなので、こちらは**遅れて悪い値段で入る**ことになる。

方向は同じで、値幅の残りだけを取る形になるため、**成績を過小評価する側のバイアス**である。60件のうち最初の6件（各銘柄1件）に効く。

除外はしない。理由は2つで、除外ルールを足すと判定が複雑になること、そしてバイアスの向きが**仮説に不利な側**だからである。この条件で合格するなら、それは本来より厳しい条件で通ったことになる。**不合格だった場合にこれを言い訳に使わない。**

### 独立性についての正直な注記

6銘柄は独立ではない。仮想通貨は相関が高く、BTCが下げれば SOL も TAO も下げる。**プールした60件は、独立した60件より弱い証拠である。**

それでも1銘柄60件より良い。単一銘柄の結果は「その銘柄固有の癖」と区別がつかないが、複数銘柄で同時に見れば「戦略の性質」に近づく。金と原油は仮想通貨との相関が低いので、その2つが混ざることも助けになる。

**この弱さを承知のうえで採用する。** 弱さを後から言い訳に使わないため、ここに書いておく。

## 判定基準（開始前に確定）

終了条件は**プール合計60トレード**。到達した日に判定する。

### 主判定

**同じ性質が出るか**を見る。損益の絶対額では判定しない。

| 項目 | 過去データ（544件） | 合格ライン |
|------|-------------------|-----------|
| プロフィットファクター | 1.30 | **1.0 以上** |
| 勝率 | 40% | 30〜50% の範囲内 |
| 平均利益 ÷ 平均損失 | 約 2.0 | **1.5 以上** |

**PF が 1.0 を下回ったら不合格。** 過去の 1.30 に届かなくてよい。前向き検証で過去と同じ数字が出ることはまず無いし、それを期待するのは検証の趣旨に反する。**符号が保たれるかだけを見る。**

勝率と損益比を範囲で見るのは、「勝率90%だがPF1.0」のような、過去と別物になっている状態を弾くため。数字が良くても性質が変わっていれば、それは同じ戦略が働いているとは言えない。

### 副判定（これらは主判定を覆さない）

* 取引が **1件も出ない** 場合は、戦略ではなく設定か接続の問題を疑う。1週間で0件なら足種かシンボル解決を確認する。
* 日次・週次の損失上限に到達した場合、その時点で停止する。停止自体は失敗ではなく、リスク管理が働いた記録として残す。
* 上流の実勢スプレッドが検証時（4.5bp）から大きく変わった場合は記録に残す。銘柄の流動性そのものが変わったなら、それは戦略の問題ではない。

### 事前に決めておく「言い訳の禁止」

以下は結果が出た後に持ち出さない。

* 「相場が特殊だった」— 特殊でない相場は存在しない。
* 「あと少し件数があれば」— 60件と決めた。
* 「パラメータを少し変えれば」— 変えた時点で別の検証になる。やるなら新しい事前登録を書く。
* 「約定が模擬だから」— 器の限界は開始前に書いてある。合格・不合格どちらの解釈にも使わない。

## 事前の予想

**不合格になると予想する。** 根拠は多重比較の計算そのもので、2/6 が残ったのは偶然の期待値と一致している。

外した場合（＝合格した場合）は、次に「なぜ 1000PEPE でだけ効くのか」を説明する番になる。機構を言えないまま実弾を入れることはしない。ボラティリティが極端に高い銘柄で ATR ベースのストップが機能しやすい、という筋は考えられるが、それなら TAO でも効くはずで、実際には TAO は両期間ともマイナスだった。**説明はまだ無い。**

## 器を差し替えた理由

VST で `check --connect` を通したところ、1000PEPE の気配値がこうだった。

```
気配値  : 1000PEPE_USDT bid=0.0028269 ask=0.0029278 （スプレッド 0.0001009）
```

**351bp。** 本番板の実測は 4.5bp なので、78倍である。往復では 701bp になる。

一方、検証したい優位性は 2.3年で +30.63% / 544件、つまり**1件あたり 5.63bp** である。**測定誤差が測定対象の125倍ある。**

同じ過去データで背景のスプレッドだけ差し替えると、結果はこうなる。

| スプレッド | 成績 | PF |
|-----------|------|-----|
| 本番実測 4.5bp | +30.63% | 1.30 |
| VST実測 351bp | **−20.20%** | 0.80 |

VST で90日回して負けたとして、それは戦略が悪いのか VST の板が悪いのか区別がつかない。**判定不能な検証に90日使うのは、何もしないより悪い**（時間を使ったぶん、何か分かった気になる）。

そこで実行環境を分けた。

| 確かめたいこと | 環境 | 理由 |
|--------------|------|------|
| **戦略の優位性** | シャドー実行 | 価格の質が要る。約定の質は要らない |
| **約定経路** | VST | 約定の質が要る。価格の質は要らない |

シャドー実行は本番の板を読み、約定だけ手元で模擬する。上流へは読み取りしか行わず、**発注メソッドを呼ぶ経路がコード上に存在しない**ため、`environment: live` でも実弾は動かない。テストで担保している（`tests/test_shadow_broker.py`）。

**シャドー実行で測れないもの**も明記しておく。板の厚みを超える数量を出したときの滑り、急変時に指値が届かない事象、取引所の障害。これらは模擬されない。だから合格しても、次は約定経路の確認と最小額での実弾という段階が要る。

## 手順

```bash
export BINGX_API_KEY="..." BINGX_API_SECRET="..."

# 1. 6銘柄まとめて起動（発注は外へ出ない）
scripts/forward_start.sh

# 2. 現況をまとめて見る（建玉・確定損益・件数を1画面で）
python3 scripts/forward_watch.py
python3 scripts/forward_watch.py --watch    # 10秒ごとに更新

# 3. 生存確認だけでよければ
scripts/forward_status.sh

# 4. 判定（60件到達後）
python3 scripts/forward_judge.py
```

銘柄ごとに詳しく見たいときは、通常のコマンドに設定を渡せばよい。

```bash
zerotrade -c config/forward/pepe.yaml dashboard
zerotrade -c config/forward/pepe.yaml report -o state/forward/pepe/report.html
```

`forward_start.sh` は既に動いているものを再起動しない。**二重起動すると同じ記録DBを2プロセスが書き、トレードが重複して数えられる**ため。

落ちていたものだけ再開したい場合も、同じコマンドでよい。

**BingX の残高がゼロでも動く。** シャドー実行の資金は模擬（各口座100万USDT）なので、入金を待つ必要はない。

`fallback_to_paper: false` にしてあるので、認証情報が読めなければ起動時に落ちる。**黙って PaperBroker に落ちたまま90日回す**のが最悪の事故なので、そこは塞いである。

## 90日のあいだに起きること

### プロセスが落ちたら

マシンの再起動、スリープ復帰の失敗、`nohup` プロセスの終了。90日あれば必ず起きる。

**建玉と残高はファイルに保存してあるので、再起動しても引き継がれる**（`state/forward/<銘柄>/shadow_state.json`）。約定のたびに保存し、書き込み途中で落ちても壊れたファイルが残らないよう一時ファイル経由で置き換えている。

保存していなかった場合に何が起きるかを書いておくと、**再起動のたびに保有中の建玉が消える**。しかも消えるのは「そのとき持っていた取引」なので、**長く持っている取引ほど失われる**。トレンドフォローは大きく勝つ取引ほど長く持つため、成績を系統的に過小評価することになる。判定を歪める側のバイアスなので、ここは潰しておく必要があった。

### 生きているかの確認

```bash
scripts/forward_status.sh              # 6本の生存確認
python3 scripts/forward_watch.py       # 建玉・確定損益・件数
tail -20 logs/forward-pepe.out         # 個別のログ
```

落ちていたら、同じコマンドで再開してよい。**再開は検証のやり直しにはならない**（状態を引き継ぐため）。ただし止まっていた期間に出たシグナルは取り逃がすので、長く止めるほど取引数が減る。

### 意図的に止めるとき

```bash
zerotrade -c config/forward/pepe.yaml stop     # 銘柄ごとに緊急停止を要求
```

## 途中経過を見るときの注意

見るのは構わないが、**見て設定を変えたらそこで検証は終わる。** 変えるなら新しい事前登録を書き、期間を数え直すこと。

途中で「勝っている」ことを確認して安心するのも、「負けている」ことを見て早めに止めたくなるのも、どちらも判定を歪める。90日という期間は、そういう判断を挟まないために先に決めてある。
