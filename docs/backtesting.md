# バックテストの進め方

このドキュメントは「どう実行するか」だけでなく、**どうすれば自分を騙さずに済むか**を主題にしている。手順だけ知りたい場合は「最短の流れ」だけ読めばよいが、実弾を入れる前には後半も読んでほしい。

---

## 最短の流れ

```bash
pip install -e ".[dev,ui]"

# 1. データを用意する（下のいずれか）
zerotrade import --csv DAT_ASCII_USDJPY_M1_2024.csv --resample H1 -o data/USDJPY_H1.csv

# 2. 検証する
zerotrade backtest --csv data/USDJPY_H1.csv --report state/backtest.html

# 3. レポートを開く
open state/backtest.html
```

出力はこうなる。

```
銘柄: USD_JPY
期間: 2024-01-04 〜 2024-12-31（6174 本）
結果: 損益 +187,759 (+18.78%) / 176件 / 勝率 38% / PF 1.37 / 最大DD -79,665
比較: 単純保有なら +8.92% → 戦略は上回った
記録: state/backtests/backtest-20260808-084048.db
```

**「比較」の行を最初に見ること。** 損益がプラスでも、単純に買って持っていただけの成績を下回っているなら、その戦略に労力を割く理由はない。

## データを用意する

### 方法A: 手元のファイルを取り込む（`import`）

無料のヒストリカルデータは提供元ごとに形式が違い、ほとんどが1分足である。`import` が形式の判別と足種の変換を引き受ける。

```bash
# 形式は自動判別される
zerotrade import --csv <ファイル> --resample H1 -o data/USDJPY_H1.csv
```

対応形式は次のとおり。

| 形式 | 見た目 | 既定のタイムゾーン |
|------|--------|------------------|
| `histdata` | `20240102 000000;140.1;140.2;...`（セミコロン・ヘッダ無し） | 米国東部（夏時間なし） |
| `mt4` | `2024.01.02,00:00,140.1,...`（日付と時刻が別列・ヘッダ無し） | EET（冬 UTC+2 / 夏 UTC+3） |
| `dukascopy` | `Gmt time,Open,High,...` | UTC |
| `generic` | ヘッダ付きCSV。列名の揺れは吸収する | UTC |

**タイムゾーンは静かに検証を壊す。** ずれたまま走らせても数字は普通に出るので気づけない。取引時間帯フィルタも日次損失のリセットもずれる。既定値が合っていない場合は `--tz Asia/Tokyo` のように明示すること。

MT4のオフセットが分からないときは、週末ギャップの位置から実測できる。FX市場は金曜17時ニューヨーク時間（夏 21:00 UTC / 冬 22:00 UTC）に閉まるので、そのクローズがサーバー時刻の何時に現れるかを見ればよい。

### 方法B: 公開ソースから取得する（`download`）

口座がなくても取れる。ただし非公式・無保証のエンドポイントなので、戦略のふるい分け用と考えること。

```bash
zerotrade download --provider yahoo --symbol USD_JPY --granularity H1 --days 720
zerotrade download --provider stooq --symbol USD_JPY --granularity D1 --days 3650
```

Yahoo は足種ごとに遡れる上限がある（1分足=7日 / 5分足=60日 / 1時間足=730日 / 日足=制限なし）。上限を超える指定は警告を出して切り詰める。

### 方法C: ブローカーAPIから取る（`fetch`）

もっとも品質が高い。実際に発注する相手のデータで検証できる。

```bash
export OANDA_ACCOUNT_ID="101-xxx-xxxxxxx-xxx"
export OANDA_API_TOKEN="..."
zerotrade -c config/oanda.yaml fetch --symbol USD_JPY --granularity M5 --days 365
```

1リクエストの上限（OANDA v20 なら5000本）は自動で分割して遡る。

> OANDA証券の REST API はデモ口座では使えない。本番口座（NYサーバーのプロコース）・会員ステータス Gold・口座残高25万円以上が条件になっている。

## 検証する

### 単一銘柄

```bash
zerotrade backtest --csv data/USDJPY_H1.csv
```

### 複数銘柄（多通貨ペア）

`--csv` を並べるだけでよい。銘柄名はファイル名から推測されるが、`--symbol` で明示もできる。

```bash
zerotrade backtest \
  --csv data/USDJPY_H1.csv --csv data/EURJPY_H1.csv --csv data/GBPUSD_H1.csv
```

**銘柄ごとに歯抜けの位置は違う。** 祝日、流動性の薄い時間帯、提供元の欠損。揃っていないまま流すと銘柄ごとに時計が別々に進み、「Aは3月、Bは5月」を同時に見ながら取引する状態になる。そのずれは損益に現れないので気づけない。そこで入口で共通の時刻へ揃えている。共通部分が極端に少ない場合はエラーで止まる。

複数銘柄のときの比較対象は「その戦略が触れた市場を等分に持つ」ことになる。分散を売りにする戦略ほど、この基準と比べなければ意味を持たない。

### パラメータを変えて試す

```bash
zerotrade backtest --csv data/USDJPY_H1.csv --param entry_period=40
```

## パラメータ掃引と、その危険性

```bash
zerotrade optimize --csv data/USDJPY_H1.csv \
  --param fast_period=10,20,40 --param atr_stop_multiplier=2,4,6 --top 5
```

**この機能は自分を騙すための道具になりやすい。** 全期間で最も成績の良い組み合わせを選べば、その数字は必ず良く見える。過去にいちばん都合よく当てはまるものを選んだのだから当然で、それが将来も効くかはまったく別の話である。

そこで探索と評価は最初から分けてある。足を前半（in-sample）と後半（out-of-sample）に割り、探索は前半だけで行い、選んだパラメータを後半で答え合わせする。

```
1. atr_stop_multiplier=4 fast_period=40 slow_period=100
    in : 損益 +59,462 (+5.95%) / 35件 / 勝率 66% / PF 1.75 / 単純保有 +4.21% → ○
    out: 損益 -30,225 (-3.02%) / 11件 / 勝率 36% / PF 0.48 / 単純保有 +5.03% → ×  ×
```

これは実際の出力である。in-sample で PF 1.75・勝率66%という魅力的な数字を出した組み合わせが、後半では PF 0.48 に崩れている。**このリポジトリで試した18通りの掃引では、上位5件がすべて out-of-sample で負けた。**

順位付けは素の損益ではなく、純損益をドローダウンで割った値を既定にしている。「最終的にいくら増えたか」だけを見ると、途中で口座の半分を溶かす経路も高く評価されてしまうからである。トレード数が5件未満の組み合わせは統計として意味を持たないので強く減点する。

## 結果を見る

```bash
# 検証と同時にHTMLを出す
zerotrade backtest --csv data/USDJPY_H1.csv --report state/backtest.html

# 後から記録を読んで出す
zerotrade report -o state/report.html
```

レポートには equity カーブ、トレード履歴、**リスク検査で却下された注文の内訳**、運用の節目が載る。却下の内訳は「フィルタが厳しすぎるのか、戦略自体が弱いのか」を切り分ける一次情報になる。

`zerotrade dashboard` でターミナルからも見られる。取引プロセスとは別プロセスで動き、SQLite を読むだけなので、検証中でも運用中でも開ける。

## 自分を騙さないための7項目

実弾を入れる前に、この順で確認してほしい。上ほど重要である。

**1. 単純保有と比べたか。** 上昇相場ではゼロを基準にすると「プラスだから勝ち」と錯覚する。2024年のドル円は年間 +11.7% で、何もしなくてもそれだけ増えた。

**2. 検定用データに一度しか触れていないか。** 検定用データを見て調整した瞬間、それは開発用データに変わる。「あと1回だけ」を許すと、この検証全体が無意味になる。

**3. スプレッドは実勢に合っているか。** 短期戦略ではここが成績を支配する。同じ戦略・同じデータで、0.3銭なら -8%、2銭なら -48% と6倍の差が出た実測がある。

**4. 期間は十分か。局面は偏っていないか。** 1年では上昇局面しか含まないことがある。下落局面とレンジ局面を含む複数年が要る。

**5. パラメータ感度はなだらかか。** 良いパラメータの周りが「なだらかな山」になっていれば信頼できる。1点だけ突出して尖っているなら過学習である。隣の値で成績が崩れる設定を実弾に使ってはいけない。

**6. プラセボは平らか。** 理屈のない条件（無関係な時間帯、無関係な銘柄）で同じ戦略を回したとき、成績が平らになるか。プラセボまで儲かるなら、それは戦略ではなく相場のドリフトを拾っているだけである。

**7. なぜ儲かるのかを説明できるか。** これが最後にして最重要である。データを掘って見つけた偏りは、理屈が無いので消えたときに何も残らない。逆に「誰が、なぜ、価格の有利不利を無視して売買しているのか」を先に説明できるなら、その仮説は1回の検定として扱える。総当たりで見つけた条件は多重検定のペナルティを払うが、事前に指定した仮説は払わない。この差は決定的である。

## 実測された数字

このリポジトリで実際に測った結果を残しておく。すべて USD/JPY、スプレッド 0.3銭、初期資金100万円、1トレードあたりリスク1%。

開発用は2024年（HistData・37万本の1分足）、検定用は2025年8月〜2026年6月（MT4エクスポート・34万本）。取得元も期間も重ならない。

| 戦略 | 足種 | 2024（開発用） | 2025-2026（検定用） |
|------|------|---------------|-------------------|
| 単純保有 | — | +9.7〜11.6% | +7.8〜10.5% |
| `sma_rsi` | H1 | -14.8%（PF 0.70） | -1.1%（PF 0.98） |
| `donchian` | H1 | +18.8%（PF 1.37） | -7.4%（PF 0.87） |
| `tokyo_fix` | M5 | +29.7%（PF 1.46） | +14.4%（PF 1.27） |
| `tokyo_fix` プラセボ(14:00) | M5 | -0.1%（PF 1.00） | +0.7%（PF 1.01） |

`donchian` は開発用データで単純保有の倍を出したが、検定用データで負けた。しかもその +18.8% はパラメータ調整の結果ですらなく、教科書的な既定値のままの数字だった。**調整していなくても再現しないことがある。**

`tokyo_fix` は両期間で単純保有を上回り、プラセボは両期間で平らだった。現時点で唯一再現している。ただし成否は執行コストに強く依存し、スプレッドが1.5銭まで広がると単純保有に届かなくなる。詳細は [strategies.md](strategies.md) を参照。
