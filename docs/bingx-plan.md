# BingX でのテスト計画

当面 BingX だけを使う前提での、実弾に至るまでの段取り。

**現状: 実弾の注文は一度も出していない。** バックテスト、VST（デモ）、シャドー実行（実勢価格を読むだけ）しか動かしていない。

---

## 全体像

2本の作業が**並行して**走る。互いに独立しているので、片方の結果を待つ必要はない。

```
配管テスト      [A] 読み取り確認 → [B] 本番最小サイズで1往復
                     （その日のうちに終わる）

前向き検証      [C] シャドー実行を90日 ────────────────────→ [D] 判定
                     （今日から2026-11-06まで）

                                                      両方通れば → [E] 実弾（最小額）
```

分けている理由は、**確かめたいものが違うから**である。

| | 確かめたいこと | 必要なもの | 環境 |
|---|--------------|-----------|------|
| 配管テスト | 注文が実際に通るか | 約定の質 | 本番・最小サイズ |
| 前向き検証 | 戦略に優位性があるか | 価格の質 | シャドー実行 |

1つの環境で両方をやろうとすると、どちらも中途半端になる。VST は約定の質はあるが板が本番と別物（1000PEPE で78倍のスプレッド）で、シャドー実行は価格が本番だが約定が模擬である。**それぞれの得意な側だけを使う。**

---

## [A] 読み取り確認（発注なし・所要5分）

```bash
export BINGX_API_KEY="..." BINGX_API_SECRET="..."
zerotrade -c config/verify.yaml verify --dry-run
```

接続、残高照会、気配値取得、建玉照会、足の取得、未確定足の判別を確認する。**注文は一切出さない。**

### 通過条件

すべて `OK` であること。特に次の2点。

* **残高がゼロでないこと.** ゼロだと [B] で発注が通らない。BingX の先物口座に10ドル程度の USDT が必要。
* **既存の建玉が無いこと.** あると [B] の判定が濁る。先に手仕舞う。

### ここで落ちたら

`requires "apiKey" credential` なら環境変数が読めていない。`does not have market symbol` ならシンボルの解決に失敗している（エラーに候補が出る）。どちらも [B] へ進む前に潰す。

---

## [B] 本番最小サイズで1往復（実弾・所要5分）

```bash
zerotrade -c config/verify.yaml verify --symbol BTC_USDT
```

確認プロンプトが出る。`y` を打つと**本物の注文が飛ぶ**。

### なぜ本番なのか

VST でも同じ手順は踏めるが、VST の約定エンジンが本番と同じとは限らない。**本番で初めて注文を出す瞬間を、90日後の判定直後ではなく今日にしておきたい。** そのときに「初めてのこと」が減っているほど安全である。

コストは BTC 0.0001 枚（約6〜7ドル相当）の往復で、スプレッド 0.03bp と手数料を合わせて数セント。**未知を潰す対価として安い。**

### 確認する項目

| 項目 | 落ちると何が起きるか |
|------|-------------------|
| 新規注文 | 注文が通らない |
| **ストップの添付** | **建玉が無防備になる。プロセスが落ちたら誰も見ていない** |
| 冪等キーの往復 | 再送時に二重発注のおそれ |
| 建玉の反映 | 「建玉が無い」と誤認して二重に建てる |
| **決済注文（reduce_only）** | **決済のつもりが反対側の新規建てになる** |
| 建玉の解消 | 上と同じ。建玉が減らず増える |
| 確定損益の取得 | 日次・週次の損失上限が働かない |

太字の項目が本命である。過去に PaperBroker 上で実際に起きた不具合で、2年ぶんのバックテスト結果が +16% から −14% にひっくり返った。実物でも同じことが起きないかを確かめる。

### 安全装置

* 途中で失敗しても、**最後に必ず決済を試みる**（`finally` で実行）。
* 決済できなかった場合は、合格と報告せず「建玉が残っています」と明示して終了コード1で落ちる。
* ストップは買値の80%に置く。検証中に引っかかって経路の確認が濁らないようにするため。

### 通過条件

すべて `OK` かつ、建玉が残っていないこと。**1つでも NG があれば実弾には進まない。**

### 実行後にやること

BingX の画面で建玉がゼロになっていることを目視で確認する。ツールの報告とブローカーの画面が一致していることまで含めて、この段階の確認である。

## [C] 前向き検証（90日・発注なし）

```bash
nohup zerotrade -c config/pepe-forward.yaml run > logs/pepe-forward.out 2>&1 &
zerotrade -c config/pepe-forward.yaml dashboard    # 別ターミナル
```

シャドー実行なので**注文は外へ出ない**。VST の残高がゼロでも動く。[A][B] と同時に走らせて構わない。

判定基準は [forward-test.md](forward-test.md) に開始前に確定してある。要点だけ再掲する。

* 期間は **90日**（2026-08-08 〜 2026-11-06）。延長も短縮もしない。
* **PF が 1.0 を下回ったら不合格。** 過去の 1.30 に届く必要はない。
* 勝率 30〜50%、平均利益÷平均損失 1.5以上（性質が変わっていないかの確認）
* 途中で設定を変えたらそこで検証は終わり。変えるなら数え直す。

**事前の予想は不合格。** 6銘柄試して2つが両期間プラスになったのは、偶然の期待値（1.5個）そのものだからである。

### 途中で見てよいもの

```bash
zerotrade -c config/pepe-forward.yaml report -o state/pepe-forward/report.html
```

見るのは構わないが、**見て何かを変えたら検証は終わる**。勝っているのを見て安心するのも、負けているのを見て早く止めたくなるのも、どちらも判定を歪める。

## [D] 判定（2026-11-06）

`forward-test.md` の「結果」欄を埋める。合否は基準に照らして機械的に決める。

**不合格だった場合**、それは失敗ではない。1000PEPE の +30.63% が何だったのかがはっきりする。次は `hypotheses.md` に挙げた未検証の機構（現物ETFの設定・解約、限月最終取引日など）へ進む。**「消せない事情を持つ参加者」がいるかどうか**を基準に候補を選ぶ。

**合格だった場合**、次にやるのは実弾ではなく**説明**である。なぜ 1000PEPE でだけ効くのか。ボラティリティが高いから、という筋なら TAO でも効くはずだが実際は両期間ともマイナスだった。機構を言えないまま金額を上げることはしない。

## [E] 実弾（[B][D] 両方が通った場合のみ）

ここまで来て初めて、実弾の話になる。

### 段取り

1. **最小額から.** 口座残高の1%を上限にする。`max_risk_per_trade` ではなく、**口座に置く金額そのものを絞る**。失っても困らない額だけを入れる。
2. **1銘柄だけ.** 分散はしない。この段階で確かめたいのは「シャドー実行と実弾で結果が食い違わないか」であり、銘柄を増やすと何が原因か分からなくなる。
3. **シャドー実行を止めない.** 同じ設定で並走させ、**両者の成績を突き合わせる**。乖離が大きければ、それが約定の質（滑り・板の厚み）のコストである。この数字は他のどこでも手に入らない。
4. **30日回してから判断する.** 増額はそのあと。

### 実弾に入る前のチェックリスト

* APIキーに**出金権限が付いていない**こと（何度でも確認する）
* IP制限をかけるなら固定IPであること（自宅回線だと変わって全部弾かれる）
* `mode: live` と明記していること（これが無いと起動時に拒否される）
* `fallback_to_paper: false` であること（黙ってペーパーに落ちないため）
* 日次・週次の損失上限が意図した値であること（`check` で確認）
* 停止手段を試してあること（`zerotrade stop` が効くか、事前に一度試す）

### 実弾でも変えないこと

**判定基準を後から緩めない。** 実弾を入れると、損失が出たときに「もう少し様子を見よう」と思いたくなる。日次・週次の損失上限はそのためにある。止まったら止まったこととして受け入れる。

## いま何が分かっていて、何が分かっていないか

| | 状態 |
|---|------|
| 発注経路（モック） | 検証済み（420テスト） |
| 発注経路（実物） | **未検証** → [A][B] で潰す |
| 戦略の優位性（過去データ） | 判定基準を満たしたものは無い |
| 戦略の優位性（未見データ） | **未検証** → [C][D] で測る |
| 約定の質（滑り・板の厚み） | **未検証** → [E] でシャドーとの差から測る |

3つの「未検証」のうち、2つは今日から潰せる。3つ目は前の2つが通ってからになる。
